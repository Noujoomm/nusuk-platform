# مواصفة نموذج جودة التقرير — v2.5 (التدرّج السلس)

> الحالة: مُنفَّذ. الملف: `apps/api/src/analytics/calculators/report-quality.calculator.ts`
> النسخة الاحتياطية المجمَّدة: `report-quality.calculator.v2.ts`
> مفتاح التبديل: `USE_QUALITY_V25` (الافتراضي: v2.5؛ `=false` يرجع إلى v2)

---

## 1. لماذا v2.5

v2 كان يعطي كل محور **درجات قفزية منفصلة** (مثلاً العمق واحد من `{0,5,10,15,20,25}`). متوسط تقريرين يقع على شبكة ضيّقة من القيم، فكانت مسارات مختلفة تعرض **نفس الرقم** ("عالقة عند 40.5٪ / 67.5٪").

v2.5 يُبقي **نفس المحاور الخمسة ونفس الأوزان** (30/25/20/15/10) — ويستبدل فقط *دالة كل محور* من درجية إلى **مستمرة**، فيصبح أي رقم بين 0–100 قابلاً للتحقيق، و 100 قابلة فعلاً.

**لم يتغيّر**: المعادلة المركّبة `جودة × 0.60 + تفاعل قائد × 0.40`، حساب تفاعل القائد، الـ API endpoints، schema الـ DB، النظام القديم 70/30.

---

## 2. المعادلة

```
finalScore = completeness + depth + attachments + metadata + structure   // مجموع 0–100
```

| المحور | الوزن (النقاط القصوى) | المدخل |
|--------|----------------------|--------|
| اكتمال الحقول | 30 | طول العنوان + طول الإنجازات + وجود المسار/التاريخ |
| عمق المحتوى | 25 | طول حقل `achievements` |
| المرفقات | 20 | عدد المرفقات الصالحة + إجمالي حجمها |
| الميتاداتا | 15 | طول `kpiUpdates` + `upcomingTasks` + `challenges` |
| الكتابة المنظَّمة | 10 | عدد الأسطر + تنوّع علامات التنسيق |

`finalScore` = مجموع مساهمات المحاور الخمس. الأوزان تجمع 1.0 بالضبط. لا multiplier ولا ceiling خفي — السقف الوحيد هو أن كل محور محدود بنقاطه القصوى.

## 3. شرح كل محور (مع المنطق)

### 3.1 اكتمال الحقول (30)
```
titlePts  = min(titleLen / 10, 1) × 10        // كامل عند 10 أحرف
achPts    = min(achLen   / 50, 1) × 10        // كامل عند 50 حرفاً
structPts = (مسار موجود ? 5 : 0) + (تاريخ موجود ? 5 : 0)
total     = titlePts + achPts + structPts
```
العنوان والإنجازات يأخذان **نقاطاً جزئية** بدل عتبة صلبة. المسار/التاريخ يبقيان ثنائيين (لا يوجد "نصف مُعرّف مسار").

### 3.2 عمق المحتوى (25) — منحنى مقعّر
```
ratio    = min(achLen / 500, 1)
depthPts = 25 × ratio^0.7
```
الأس `0.7 < 1` يجعل المنحنى **مقعّراً**: يكافئ البداية (أول 100 حرف تعطي أكثر من آخر 100)، مع تناقص العائد. كل طول من 0–500 يعطي رقماً مميزاً.

| طول الإنجازات | درجة العمق (من 25) |
|---------------|---------------------|
| 50  | 4.99 |
| 100 | 8.10 |
| 200 | 13.16 |
| 300 | 17.49 |
| 500 | 25.00 |
| 800 | 25.00 (مُشبَع) |

### 3.3 المرفقات (20) = عدّ (15) + حجم (5)
```
countPts = 15 × min(validCount / 3, 1)              // كامل عند 3 مرفقات صالحة
bytesPts = 5  × min(totalValidBytes / 1MB, 1)       // مكوّن مستمر يكسر التكميم
total    = countPts + bytesPts
```
"صالح" = حجمه > 10KB ونوعه ضمن القائمة المعتمدة. المكوّن الحجمي يجعل تقريرين بنفس عدد المرفقات لكن بأحجام مختلفة يحصلان على درجات مختلفة.

### 3.4 الميتاداتا (15) — نقاط جزئية لكل حقل
```
fieldPts(f) = 5 × min(len(f) / 40, 1)
total       = fieldPts(kpiUpdates) + fieldPts(upcomingTasks) + fieldPts(challenges)
```
بدل "موجود = 5 / غير موجود = 0"، الحقل القصير (10 أحرف) يأخذ 1.25، والكامل (≥40 حرفاً) يأخذ 5.

### 3.5 الكتابة المنظَّمة (10) — إشارة متدرّجة
```
lineComponent   = min(عدد الأسطر غير الفارغة / 4, 1)
markerComponent = (أنواع علامات التنسيق الموجودة من: تعداد/عناوين/تشديد) / 3
total           = 10 × (0.6 × lineComponent + 0.4 × markerComponent)
```
v2 كان boolean صرف (10 أو 0). v2.5 يسمح بدرجة بينية للتقرير "نصف المنسَّق".

## 6. الأثر على اللوحة

- البطاقات الثلاث **بلا تغيير في الـ layout**.
- التغيير الوحيد: سطر "📄 2 تقرير (1 جيد، 1 مقبول)" أصبح "📄 2 تقرير · متوسط الجودة 67.5٪ (التوزيع كتفصيل باهت)".
- ⚠️ **سقف الـ60٪ البنيوي خارج نطاق v2.5**: تفاعل القائد يرجع 0 للجميع غالباً (لا مصدر بيانات لـ reportReviews/meetings/reactions/logins)، فتبقى `finalScore = avgQuality × 0.6`. v2.5 يحلّ **تكتّل الأرقام** لا سقف الـ60٪. معالجة تفاعل القائد قرار منفصل.

---

## 7. الترحيل والتراجع

- **لا backfill مطلوب**: اللوحة تحسب live → التغيير يظهر فوراً. اللقطات التاريخية في `DailyTrackPerformance` تبقى بـ v2 (لا قيمة في إعادة حسابها — التركيز على المستقبل).
- **التراجع الفوري**: ضع `USE_QUALITY_V25=false` في متغيرات بيئة Railway → الدالة ترجع إلى v2 المجمَّد بدون redeploy للكود.
- المفتاح يُقرأ عند كل استدعاء، فالتبديل لا يتطلب إعادة بناء.

## 8. FAQ للموظفين

**لماذا تغيّرت درجتي؟**
النظام انتقل من تقييم بفئات خشنة (ممتاز/جيد/مقبول) إلى تقييم رقمي دقيق. درجتك الآن تعكس **التقدّم الفعلي** في كل محور، لا أقرب فئة.

**كيف أحسّن درجتي؟**
- اكتب حقل "الإنجازات" بتفصيل أعمق (المنحنى يكافئ حتى 500 حرف).
- أرفق ملفات داعمة (PDF، صور، Excel) — العدد والحجم كلاهما يُحتسب.
- املأ حقول kpiUpdates / المهام القادمة / التحديات بمحتوى فعلي (≥40 حرفاً لكل حقل لنقاط كاملة).
- نظّم "الإنجازات" بأسطر متعددة وتعداد/عناوين.

**ما الفرق بين 87٪ و 92٪؟**
في v2 كانا قد يظهران كرقم واحد. الآن الفرق حقيقي: 5 نقاط أكثر من العمق أو الميتاداتا أو التنظيم. كل نقطة لها سبب رقمي مرئي في تفصيل الدرجة.

**هل التقييم عشوائي أو يعتمد على ذكاء اصطناعي؟**
لا. دالة رياضية بحتة وحتمية — نفس التقرير يعطي نفس الدرجة في كل مرة، دائماً.
